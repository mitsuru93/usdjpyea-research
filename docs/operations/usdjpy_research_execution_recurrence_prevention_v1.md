# USDJPY Research Execution Recurrence Prevention v1

This document is mandatory before any long-running USDJPY research, candidate evaluation or MT4 workflow.

Latest amendment: 2026-07-24 after RQ-020E, RQ-021, RQ-022 and HYP-023 execution review.

## 1. Authority-direction gate

Before changing timestamps, fields, keys or data, record:

- source authority period and lineage;
- period being transformed;
- immutable periods and files;
- exact reproduction gates against the authority;
- whether any existing result will be recomputed.

If the proposed work changes the authority period when the user directed the other period to conform, stop before implementation.

## 2. Evaluator-source and identity gate

A scientific evaluator may not run unless:

- its complete source is committed on the working branch;
- the exact commit, blob SHA and source SHA-256 are recorded;
- syntax/static checks pass for every imported module;
- all imports are resolved against a declared capability matrix;
- all inputs are identified by path, artifact ID, digest and SHA-256;
- a one-row or one-period dry run passes;
- output schema and deterministic hashes are generated by code.

An execution-script hash without committed source is not an adequate reproducibility contract.

A subset library may not be imported into a full-universe evaluator unless every requested family/function is asserted before data loading. Missing capability must stop in preflight, not during signal materialization.

## 3. Algebraic-derivability disclosure

Before calling a family blind or preregistered, determine whether its payoff is algebraically derivable from already opened development outcomes. Examples include reversing a known trade, scaling a known P/L, or replacing a known exit with a deterministic transformation.

If derivable:

- state that the action is development-outcome-derived;
- calculate the feasible aggregate and any already determined gates before expensive execution;
- do not claim that outcomes were unavailable;
- do not relax a gate that is already false;
- freeze only the unseen 2025 implementation and binding gate prospectively.

## 4. Impact-sufficiency gate

Before opening a family, estimate:

- loss source to be addressed;
- affected trade count and months;
- maximum development impact available from the mechanism;
- winner/profit harm;
- whether the mechanism can plausibly close the target deficit.

Reject a family before preregistration when its reachable effect is materially smaller than the loss source. Do not spend a full PR/CI cycle on an impact-insufficient local repair.

## 5. Technical feasibility preflight

Before the full grid:

- assert RangeIndex and timestamp monotonicity;
- inventory missing checkpoints, period endpoints and delayed bars;
- prove trade-key uniqueness and accepted-key reconciliation;
- test one representative candidate and one trade per period;
- verify same-month and hard-exclusion semantics;
- test output writes and programmatic SHA manifest generation;
- record failure artifacts without treating them as scientific results;
- verify that every protocol path exists and is readable;
- verify that the committed protocol SHA matches the local file used by the command;
- execute a `--preflight-only` mode that cannot construct signals or P/L.

## 6. One-stage-one-PR packaging

A stage should normally contain one atomic package:

- preregistration or fixed-cohort protocol;
- committed evaluator;
- result JSON and report when outcomes are authorized;
- ledger addendum;
- registry;
- period-policy pointer;
- memory manifest;
- validator changes only when required.

Run local/static validation before opening the PR. Do not create serial micro-PRs for files that belong to the same scientific decision.

For a multi-file package, assemble all files before the first repository write. Prefer one Git tree/commit or one local commit over sequential Contents API micro-commits. A PR with many connector-generated commits is permitted only when the connector cannot batch safely, and the reason must be recorded.

## 7. CI and Runner efficiency

Use GitHub-hosted runners for artifact download, Python, CSV/JSON analysis and hash verification. Use `onamae-mt4-ui-01` only for Rakuten MT4/GUI work and `onamae-mt4-01` only for VPS-local non-GUI work. Follow the Core MT4 runbook and the tester-automation handoff.

After opening a PR, poll combined status at meaningful intervals. Fetch job logs only on failure. Do not add status workflows merely to observe another run.

## 8. Canonical state and Notion synchronization

GitHub remains canonical. After merge:

1. read back main commit, registry, question and next action;
2. update Notion Current State properties and body pointers;
3. update the active task properties and body status;
4. fetch both Notion pages back;
5. compare commit, registry, question/hypothesis, status, next action and canonical file pointers;
6. only then mark the stage complete.

Updating properties alone is not synchronization when the page body still names an older registry, question or authorization boundary. A stale Notion page must be labeled stale rather than presented as current.

## 9. Stop-safe WIP boundary

If a task stops before an atomic stage is complete, write a WIP receipt containing:

- branch and head SHA;
- files completed;
- files missing;
- whether outcomes were accessed;
- current scientific status;
- exact next action;
- explicit `NOT_CANONICAL` marker.

Do not leave a partial branch that can be mistaken for an authorized family.

## 10. Completion definition

A research stage is complete only when:

- exact input and source identities are verified;
- evaluator preflight and all scientific gates pass or the family is explicitly closed;
- result/report/ledger/registry/policy/next action are atomic;
- both Research CI and memory validation pass;
- main readback is verified;
- temporary workflows and superseded marker PRs are cleaned up;
- Notion properties and body both pass readback;
- the next permitted work and protected-period boundary are explicit.

Actions success alone, a local CSV alone, or an unmerged branch is not completion.

## 11. Canonical-head lock before work

Before reading a prior summary, continuing a branch or creating a new branch:

1. fetch the latest Research `main` SHA;
2. fetch the manifest and current registry from that exact SHA;
3. compare any proposed branch base with current `main`;
4. enumerate open WIP branches/PRs that could contain newer work;
5. record `BASE_IS_CURRENT=true` before analysis or writes.

If the planned branch is behind main or the summary points to an older registry, stop and rebase/restart from current main. Do not spend time extending an obsolete branch.

## 12. Source-transfer integrity gate

For evaluator source transferred through a connector:

- split source into modules before transfer when a file is large or has multiple responsibilities;
- never rely on an unverified long inline/base64 transfer;
- fetch every written file back;
- verify local SHA-256, Git blob SHA, byte count and line count;
- run syntax/import checks against the fetched-back source;
- block outcome authorization until all identities match.

A suspected truncation or encoding change is a technical incomplete attempt even when no runtime error occurred.

## 13. Command and path manifest

Every executable stage must have a committed or generated run manifest containing:

- repository commit;
- evaluator/module paths and SHAs;
- protocol path and SHA;
- input paths and SHAs;
- output directory;
- exact command;
- working directory;
- preflight result;
- whether outcomes are permitted.

The command must be generated from the manifest. Hard-coded ad hoc local paths are prohibited. Path existence and SHA checks run before importing data.

## 14. Required-output completeness gate

Before unlocking outcomes, compare the preregistration `required_outputs` against an evaluator output manifest.

The preflight must fail if any required output is absent, including:

- signal/trade ledger;
- fold/month/quarter/direction metrics;
- default/severe net and PF;
- ex-best-two and concentration;
- boundary-liquidation sensitivity;
- realized balance drawdown;
- parameter equivalence;
- adjacency/family-region result;
- output SHA manifest.

A post-result summarizer may describe frozen results, but it must not be required merely because the evaluator omitted a preregistered output.

## 15. Tool and write plan

Before the first connector write, record:

- tools/actions required for the whole stage;
- files to create/update;
- which writes can be batched;
- CI checks expected;
- Notion pages to update;
- readback checks.

Discover each connector schema once and reuse it. Repeated tool discovery and file-by-file improvisation are treated as avoidable execution overhead.

## 16. Failure classification and retry budget

Every abnormal stop is classified immediately as one of:

- `TECHNICAL_INCOMPLETE_NO_DATA_LOAD`;
- `TECHNICAL_INCOMPLETE_NO_OUTCOMES`;
- `SCIENTIFIC_RESULT_COMPLETE_FAIL`;
- `SCIENTIFIC_RESULT_COMPLETE_PASS`;
- `STATE_SYNC_INCOMPLETE`;
- `WIP_NOT_CANONICAL`.

For the same root cause, permit one repaired retry. A second recurrence blocks further execution until the prevention control is added and validated. Failed technical attempts never count as scientific runs.

## 17. Timing and overhead receipt

Every stage expected to exceed ten minutes must record:

- UTC/JST start and finish;
- analysis/compute time;
- CI wait time;
- connector/write time;
- retry count;
- failed-attempt count;
- tool-call count if available;
- avoidable-overhead estimate and basis.

Without this receipt, do not claim an exact number of minutes lost. The postmortem must distinguish measured elapsed time from qualitative attribution.

## 18. Progress visibility

A long stage must expose a concrete checkpoint after each atomic milestone:

- current main/registry verified;
- preflight passed;
- PR opened;
- CI passed;
- outcome run completed;
- closure merged;
- Notion readback passed.

A message saying work is progressing is not a checkpoint unless it includes a commit, run, artifact, result file or verified state transition.
